WHAT TO CHECK
1. Bytes. The tarball under review is the head packed by `scripts/cert-review/pack.mjs` (as the release packs it); look at `stage.json` and its file list: only dist/, LICENSE, NOTICE, README.md and package.json, no install scripts, no dependencies. The record job checks in code that the artifact is the pack job's bytes, that its gitHead is the tag's commit and that the tag is on main; after publishing, the release's verify job checks the registry copy, its provenance and npm latest. Don't repeat them.
2. The delta and the NEGATIVEs (Lars's test ruling: every fix comes with a committed behaviour-level test that fails on the old build). For every fix and feat in plan.md, name its committed tests and show from suites.json that each is `fixed` (fails in neg, passes on tag) on at least one kernel where the fix applies. A fix with no committed test, or whose test also passes in neg on every kernel, is a test gap: a known issue, unless a kernel gate explains it (say which). Read the PR, not only its title.
3. Regressions. Every `regression` row in suites.json and every `regression` case in the fixtures, on any kernel: read the log or both outputs, re-run that one unit in its tree on that kernel, and decide: a real regression (apply the severity bar), explained by the delta (an intended change; cite the PR), or a flake. `fail-new-only` rows: re-run them in neg yourself before you decide. A flake is never just noted (Lars: no retries, find the root cause): every flake you see, including the m-fixture cases the digest lists as flipped on its diagnostic re-runs, gets an issue in ai-ecoverse/slicc-jsh (search first) with the test or fixture name, the kernel, the tree, the runner (cloud-run-bench), the log path in the run's artifacts and what the re-runs gave, and the line lists it as known. A flake does not by itself fail the release.
4. Changes against Node. Read every fixture `diff-changed` case and every row whose output `changed`: each must be explained by the delta (a fix moving toward Node is good; say so). Anything else is a finding.
5. The floor and 1.86.0. jsh's engines say slicc-kernel >=${ENGINES}. A unit that passes on prev and fails on new on 1.72.0 or 1.86.0 is a regression on that kernel even if newer kernels are fine. Pre-existing `both-fail` rows on old kernels are not findings of this change.
6. Users enforce. Everything ran under enforce. The rows must still show: a user's own files chmod and spawn like Node, another user's files are refused with Node's error shape, rm of /dev, /etc and another user's tree is refused and removes nothing, umask applies to new files and children. A regression in any of these is a security finding.
7. The browser suite: every failure read and explained, or re-run.
8. Known issues. Start from the previous certification's known list: the `cert-review` lines of the last pull requests merged to main (`gh api repos/ai-ecoverse/slicc-jsh/commits/<sha>/statuses`, or their PR comments) and every open issue. An issue this pull request claims to fix is fixed only for the checklist items its tests cover. For every item, look for its evidence in this run (the fixture, row or test, including `diff-unchanged` fixture cases). An item this change fixes must be `fixed` (step 2). Every item still present is carried: cite its issue, and if that issue is closed or only partly fixed, cite the issue that tracks the leftovers, or file one. Also list the open issues (`gh issue list -R ai-ecoverse/slicc-jsh --state open`) and carry any that applies to this change. An issue closed as not planned (`stateReason: NOT_PLANNED`) is an accepted difference, not a known issue: don't list it in `known`; at most note it in comment.md as `accepted: #<n>`.
